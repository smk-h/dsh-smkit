本文说明 dsh-smkit 的「进程资源」页：展示 dsh 宿主进程及其可发现子进程的实时资源 —— CPU（按整机容量归一）、内存（优先使用专用工作集）、累计 CPU 时间和命令行。满足应用组识别条件时，页面还会并入宿主之外的同名应用进程，用于与任务管理器的「应用」行对账。页面打开时才轮询采样；关闭后停止请求，采样助手按生命周期退出，不保留持续采样或采样后台进程。

## 一、 它是什么

### 1. 解决什么

dsh 内部拉起了哪些进程（MCP stdio 服务器、各插件 spawn 的 shell / git / npm、Windows 下 stdio 命令的 cmd 包装），各自吃多少 CPU、多少内存，此前没有任何一个界面能回答。这个页面把答案放进 dsh 自己的「更多」菜单：点开「进程资源」一行，就是宿主进程整棵子树的实时占用表。

### 2. 入口在哪，为什么没有开关

入口在左栏「更多」菜单（四宫格图标展开）里的「进程资源」行，与宿主自己的「浏览更多插件 / 创建你的插件」同列，点击切换出一块主面板。不占左栏图标条的独立图标——诊断页是偶尔打开的东西，不值一个常驻启动位；曾经评过另外三个落点（账号弹出菜单硬编码不可插、设置弹窗太窄、会话「···」菜单语义是"当前会话的操作"），更多菜单是唯一形态与语义都合适的。

技术形态：行组件优先复用宿主 `MenuItemButton`（`sidebar.panellist.actions` 座位，宿主插件菜单行用的同一个）；宿主模块表没有该导出时回落为本特性自带的一行，样式按宿主菜单行 `.item` 的实测值对齐（`13px` / `34px`、圆角 `12px`、hover 使用相同 token，实测逐项一致）。切换面板走 `ctx.layout.selectPanel`——经反射在点击时取用，宿主没有 layout 服务时只损失这一次点击，不影响插件激活。

**没有设置开关**，这是有意的：调试页需要一个开关是因为它的存在本身有含义要控制；这个页面的持续开销 —— 包括宿主侧的采样 —— 都由轮询驱动。关页后请求立即停止，Windows 常驻采样助手经过约 6 秒宽限自行退出，因此不需要再用开关控制页面是否可用。

### 3. 页面构成

页面按评审定稿的版式实现（仅「子树 CPU 构成」卡一项评审后裁掉，见总览带一条）：

- **头部**：标题 + 「采样中」心跳脉冲徽章（页面隐藏时变「已暂停」、采样器启动期为「启动中」）+ 元信息行（N 个进程 · 1 秒/次 · N 核归一；N 是这一帧采到的行数，折叠不影响它）+ 刷新。
- **总览带**：四张 KPI 卡占满——「dsh 总 CPU / dsh 总内存」（宿主 + 可发现子进程的合计，即页面可观测的 dsh 服务进程树；悬停有口径说明）与「宿主 CPU / 宿主内存」（仅宿主进程本身），大数值 + 右下角一分钟迷你趋势线（页面内存里留最近 60 个采样点，不落盘、关页即弃）。初版左侧还有一张「子树 CPU 构成」三色堆叠条卡，评审后去掉——三个份额的混合读不出可行动的结论，KPI 卡与整应用对账行已把同样的数说得更清楚。
- **一棵进程树**（一张卡、一套列，不再按类别切三块）：行按 `ppid` 嵌套，父行在前、子行缩进 `14px`。**只有带直接子进程的行显示展开箭头**，点击后折叠或展开它的整棵子树；叶子行只保留对齐占位。父子关系跨两个口径也照连 —— 桌面端 GUI 主进程是宿主的祖先，renderer 可以位于宿主的平行分支，它们和 MCP 服务器同处一棵树。任务管理器则按应用身份展示一级缩进，既不展示这棵多层树，也不保证纳入 MCP 等异名子进程。
  - 行的**类别只用一个 `7px` 色点**表达，不再有组头：蓝 = 宿主（整行淡色强调）、紫 = MCP、绿 = 其他子进程、灰 = 应用其他进程（应用组中不在宿主子树内的同名进程；它们**不计入两张「dsh 总」卡**）。色点悬停显示类别名。
  - MCP 行仍带 `mcp:<服务器名>` 紫色胶囊（工作区级服务器为 `mcp:<服务器名>@<工作区名>`；沿树继承，Windows 下 node 服务器坐在 cmd 包装下面）。
  - 兄弟之间按 CPU 降序、再工作集 `memBytes` 降序、再 `pid` 排序；默认**全部展开**（等于旧的平铺视图，但层级可见），折叠状态记在页面内存里，跟着采样刷新保留。
- **列**：进程名（悬停见完整命令行）/ PID（等宽）/ CPU%（**热力比例条**：`< 5%` 蓝紫渐变、`5%～25%` 琥珀、`≥ 25%` 红——满负载进程不读数也能找到）/ 内存（优先显示**专用工作集**，无专用读数时单行回退到工作集；有专用读数时悬停可见含共享页的工作集）/ 累计 CPU（等宽）/ 命令行（等宽弱化）。窄窗口（`≤ 980px`）收起命令行列并纵向堆叠总览带。
- **整应用对账行**（在树下、采样开销注脚上方）：`整个应用（含 GUI 进程） N 个进程 · CPU% · 专用 X（工作集 Y）`，用于与任务管理器「应用」行对账。它统计的是报告器识别出的同名应用组，不是按 Electron 角色固定挑选的 5 个进程；识别边界见 [三、2](#2-应用组进程树之外的那半个应用)。
- **采样开销注脚**：虚线边框条 + 仪表图标 + 加粗数值（`meter` 字段，见下）。

配色全部走 `--smkit-pm-*` 变量（亮色默认、`body[data-ds-dark-theme]` 切暗色），中性面与文字借用宿主 `--dsw-alias-*` 令牌，自动跟随主题；卡片底取 `--dsw-alias-bg-layer-2`（宿主嵌套面的同一层级）、条槽与展开箭头悬停底取边框令牌的半透明 veil，两个半边与主题中心的主题都不用点名。主题中心的 One Dark Pro 会整体重铺这些 alias 令牌（面板落 `#21252b`、画布 `#282c34`），仅数据五色是本页自己的，另以 `body[data-smkit-theme='one-dark-pro']` 块映射到该配色自己的语法色阶（宿主蓝→链接蓝 `#61afef`、MCP 紫→关键字紫 `#c678dd`、其他绿→字符串绿 `#98c379`、琥珀→黄 `#e5c07b`、红→`#e06c75`）。CPU 列出现 `—` 时的语义见 [二、2.3](#23-什么情况下显示)。

## 二、 数据采集与统计口径

一句话：**OS 为每个进程记录累计 CPU 时间和当前内存占用；CPU 百分比来自相邻样本的累计时间差分，内存则直接读取瞬时值**。任务管理器、Process Explorer 与本页都需要解决数据源、时间窗和归一化问题，差别在读法与口径，而不是存在一本可直接读取的“当前 CPU 百分比”账本。

```text
OS 进程账本（Win32_Process / ps）
   │  Windows 常驻 PowerShell 每约 1.2 s 吐一帧全表（单行 JSON）
   ▼
一帧 + 它的前一帧（帧对，由采样器随读取返回）
   │
   ├─ 帧对帧相减 ──────▶ CPU%
   ├─ 从宿主 pid BFS ──▶ 宿主子树
   ├─ 同名祖先链 ──────▶ 可选的应用组
   └─ 查进程登记簿 ────▶ mcp:<服务器名> 标签
   ▼
GET /smkit/api/process-monitor/sample ──▶ 页面表格
```

### 1. 数据源：OS 的账本，不是"测"出来的

Windows 上通过 WMI 的 `Win32_Process` 读，每个进程一行：

| 字段 | 含义 | 单位 |
| --- | --- | --- |
| `KernelModeTime` + `UserModeTime` | 进程自启动以来累计消耗的 CPU 时间（内核态 + 用户态） | 100 ns |
| `WorkingSetSize` | 此刻实际占用的物理内存页（驻留集，含共享页） | 字节 |
| `ProcessId` / `ParentProcessId` | 自身 pid 与父 pid —— 树的原料 | — |
| `Name` / `CommandLine` | 进程名与完整命令行 | — |

内存还有第二个来源：**专用工作集**（`Win32_PerfRawData_PerfProc_Process.WorkingSetPrivate`，用于对应 Windows 任务管理器「进程」页的「内存」列）。它不在 `Win32_Process` 里，要单独查询性能计数器类；流式采样每两帧合并一次，其余帧沿用上次的值（成本见 [二、3.3](#33-专用工作集的采样成本)）。

POSIX 上 `ps -axo pid=,ppid=,rss=,time=,args=` 一行一个进程：`time` 列就是累计 CPU 时间（`[[dd-]hh:]mm:ss[.cc]`），`rss` 就是驻留集（KiB），写入统一的 `memBytes` 字段；**没有**专用工作集的零依赖来源，页面回退到 `memBytes`。

这些值直接来自 OS 记账，但仍受采样时刻、进程退出和 PID 复用影响，不能理解成无误差、无延迟的同步快照。特别地，`ps` 自带的 `%cpu` 列（进程生命周期内的平均值）刻意不取 —— 它不对应页面上任何一个采样时间窗。

### 2. CPU 差分与无效窗口

#### 2.1 CPU% 是里程表差分

累计 CPU 时间是**里程表**，不是速度表：单独一次读数只说明"这个进程从启动到现在一共用了 3.2 s CPU"，不说明它现在多忙。要得到当前的占用率，必须两次读数相减：

```text
CPU% = (里程₂ − 里程₁) ÷ (时刻₂ − 时刻₁) ÷ 逻辑核数 × 100
```

以本机 16 逻辑核为例：某进程在 1.2 s 墙钟里里程表走了 384 ms —— `384 ÷ 1200 ÷ 16 × 100 = 2.0%`。

**为什么除以核数（整机归一）**：不除的话，一个单核跑满的进程显示 100%，除完显示 `100 ÷ 16 = 6.25%`。归一后所有进程的百分比理论上相加不超过 100%，"子树合计"才可以按整机容量理解；这也是本页与 Windows 任务管理器对账时采用的归一口径。

**内存不需要差分**：工作集或驻留集是瞬时值，读出来直接用。Windows 单行优先显示**专用工作集**，含共享页的工作集仍随行下发；有专用读数时，悬停内存格可见工作集。两者在本机一次 5 个 Electron 进程实测中分别为 482 MB 与 866 MB，差额约占工作集的 44%。这说明把工作集直接相加会把共享页重复计入，不等于专用工作集合计。

#### 2.2 差分窗口挂在帧上，不挂在轮询上

本特性修过的真问题。Windows 流式采样器是一个常驻 PowerShell，每约 1.2 s 输出一帧全表；页面每 1 s 轮询一次。轮询落点必然偶尔两次落在同一帧里 —— 早期版本把差分放在路由里（本次读减上次读），撞帧时窗口变成 0 ms，整列 CPU 一起打成"—"，且随相位漂移成串出现，页面上就是"经常性没有统计数据"。

现在**帧对（本帧 + 前一帧）由采样器随读取一起返回**。Windows 流式路径只在新帧到达时推进帧对，重复轮询同一帧只会重复显示同一组数字，不会产生零宽窗口。Windows one-shot 降级路径和 POSIX 则用相邻两次实际采样组成帧对，窗口取决于这两次采样的真实间隔。

#### 2.3 什么情况下显示"—"

进程行的 `—` 表示"没有可用的差分窗口"，共四种来源：

- **首帧或新进程**：没有前一帧，或前一帧中没有这个 PID；
- **窗口 `< 250 ms`**：两次读的是同一帧或时钟噪声；
- **窗口 `> 5 s`**：这对帧跨得太远，平均值会失真；
- **增量为负**：可能出现 PID 复用，不能把新进程的累计时间与旧进程直接相减。

四种情况都在进程行显示 `—` 而不是 0.0%，下一对有效帧自动恢复。合计字段的结构不同：`totals.cpuPct` 与 `app.totals.cpuPct` 始终是数值，无有效窗口的行按 0 参与 CPU 合计，因此不能仅凭合计为 0 判断所有进程都空闲。

### 3. 采样器与报告器

#### 3.1 分工与数据契约

对外的形状是一条只读路由，没有写操作：

```text
GET /smkit/api/process-monitor/sample
→ { sampledAt, intervalMs: 1000, platform, hostPid, cores,
    warmingUp?, error?,
    entries: [{ pid, ppid, name, cmdline, kind, mcpServer?,
                cpuPct: number | null, memBytes, memPrivateBytes?, cpuMs }],
    totals: { cpuPct, memBytes, memPrivateBytes?, count },
    app: { rootPid, rootName, entries, totals } | null,
    meter: { cpuPct: number | null, memBytes, memPrivateBytes?, count } | null }
```

- **采样器**（[`src/host/features/process-monitor/sampler.ts`](../src/host/features/process-monitor/sampler.ts)）把 OS 进程表读成归一化的行（`pid` / `ppid` / `name` / `cmdline` / `memBytes` / `privateBytes?` / `cpuMs`）并维护帧对：
  - **Windows**：默认使用**常驻流式 PowerShell**（`Get-CimInstance Win32_Process` → `Select-Object` 输出主表七个字段及合并的 `PrivateWS` → `ConvertTo-Json -Compress`，循环里 `Start-Sleep 950ms`）。常驻的原因是一次 PowerShell 启动就要零点几秒，每秒重启一个比留一个贵；脚本开头设 `[Console]::OutputEncoding=UTF8`，中文命令行才不会乱码。流连续两次停摆（4 s 无帧）就**降级为每请求一次性查询**（one-shot），本会话内不再回头。
  - **POSIX**：每次请求 spawn 一个 `ps`（几十毫秒，不值得常驻）。`args` 含空格，所以前四列按位置取、剩余整体作命令行。
- **报告器**（[`src/host/features/process-monitor/report.ts`](../src/host/features/process-monitor/report.ts)，纯函数）：给定帧对与宿主 PID，完成收子树 → 按 `excludePids` 剔除采样器 → 查登记簿标 MCP → 差分 → 识别应用组 → 汇总并排序。输入相同输出必相同，单测据此钉死每条规则。
- **路由**（[`src/host/features/process-monitor/api.ts`](../src/host/features/process-monitor/api.ts)）：不持有跨请求状态 —— 帧对由采样器随读取返回，路由只做"读一次、算一次、答一次"。

#### 3.2 为什么采样进程是 powershell.exe（Windows）/ ps（POSIX）

常见疑问：页面一打开，宿主名下就多出一个 `powershell.exe`（约 100 MB）—— 它就是**采样进程本身**：本插件用来读取全系统进程表的程序，不是被监控的对象。主进程表要一次拿全七个字段（PID、父 PID、进程名、命令行、工作集、内核态累计 CPU 时间、用户态累计 CPU 时间），专用工作集再从性能计数器类合并。Windows 上零依赖的主表候选只有 PowerShell + CIM：

| 候选 | 缺口 |
| --- | --- |
| `tasklist` | 没有 `ppid`、没有内核/用户 CPU 时间，输出还随系统语言本地化 |
| `wmic` | 微软已废弃，Win11 新版已移除，不能指望 |
| Node 原生 API | 不提供第三方进程的信息；要读进程表只能上原生模块（本插件零 npm 依赖，不引入） |
| **PowerShell + `Win32_Process`** | 全字段、随系统自带、`ConvertTo-Json` 可单行成帧 |

POSIX 上干同样活的等价物是 `ps`，两边形态相反，各取最便宜：

| | Windows | POSIX |
| --- | --- | --- |
| 采样进程 | 常驻流式 PowerShell（循环：查全表 → 吐一行 JSON → 睡 950 ms） | 每次请求 spawn 一个 `ps`，查完即走 |
| 原因 | PowerShell 冷启动 0.3～0.6 s，常驻把启动成本摊薄到一次 | `ps` 全表只要几十毫秒，常驻反而白占一份内存 |
| 关页后 | 6 s 宽限 + 一帧周期后自退（宽限防快速来回切页的启动抖动） | 最后一个 `ps` 查完即退出，不需要宽限 |
| 自我隐藏 | 正常流式路径把 PowerShell + conhost 记入 `meter` 注脚 | 目标是排除 in-flight 的 `ps`；本次读取结束时 PID 已移出跟踪集，存在未排除的时序边界，见 [六、2](#2-已知限制) |

排查口径：宿主名下那个 PowerShell 是**页面**的助手；`pm-top` 自己的采样助手挂在 pm-top 的 node 进程下、不在宿主子树内，不会作为宿主子孙出现在对照输出里（详见 [五、2.2](#22-对照工具) 的注记）。

#### 3.3 专用工作集的采样成本

零依赖来源只有性能计数器类 `Win32_PerfRawData_PerfProc_Process`。本机（16 核）实测，同一 PowerShell 进程内重复调用：

| 取法 | 冷启动一次 | 热态一次 |
| --- | --- | --- |
| `Win32_Process`（3 字段） | — | 0.17～0.18 s |
| `Win32_PerfRawData_PerfProc_Process` 全表 | 1.32 s | 0.20～0.32 s |
| 同上，按单个 PID 过滤 | 0.13 s | — |
| 同上，按 5 个 PID 过滤（OR） | 0.25 s | — |

结论：**热态代价与 `Win32_Process` 查询同量级**（冷启动那 1.3 s 是 WMI 提供程序在进程里的首次初始化），所以常驻采样器**每两帧**扫一次全表专用值，其余帧沿用上一份映射 —— 均摊约 +0.1 s/帧。每帧都扫在技术上也可行，但内存以秒为尺度变化，多花的这份 CPU 只会抬高页面自己的 `meter`，不换来多少额外信息。扫不到的 PID（映射里没有、或值为 0）按"没有读数"处理，不下发该字段；单行回退到工作集，合计的部分缺失边界见 [六、2](#2-已知限制)。

### 4. 术语与缩写

以下集中解释对账时容易混淆的术语与缩写：

| 缩写 | 全称 | 在本页/本文里指什么 |
| --- | --- | --- |
| TM | Task Manager，任务管理器 | 对账用的 Windows 工具；本文正文直接写“任务管理器” |
| WS | Working Set，工作集 | 含共享页的物理占用，对应 `memBytes`；可见于行内悬停、整应用对账行括号和 `pm-top` 输出 |
| 专用 / PRIV | Private Working Set，专用工作集 | 有读数时优先显示的内存值，对应 `memPrivateBytes`；用于对应任务管理器「进程」页的「内存」列 |
| 帧对 | frame pair | 当前样本与用于差分的前一样本，CPU% 由两者计算；前一帧对应 `SampleBaseline` |
| 应用组 | application group | 按同名祖先链和平行分支启发式识别的一组进程，数量不固定；对应 `app` / `ProcessAppScope`，见 [三、2](#2-应用组进程树之外的那半个应用) |
| meter | 采样开销足迹 | 页面底部「本页采样器另占 …」那行，对应 `ProcessMeterFootprint`；正常 Windows 流式路径不计入宿主子树合计，其他路径边界见 [六、2](#2-已知限制) |

## 三、 进程范围与应用对账

### 1. 子树与 MCP 标签

**树**：OS 记录每个进程的父 PID。报告器从 `process.pid`（即 dsh 宿主进程本身）出发做宽度优先搜索，收出可沿 `ppid` 到达的整棵子树 —— MCP 服务器、cmd 包装、conhost、其他插件 spawn 的命令都在其中。正常 Windows 流式路径会把采样器自己的子树从 `entries` 和 `totals` 中排除，并汇总成 `meter` 字段，在表格下方单列开销；one-shot 降级路径与 POSIX 的时序边界见 [六、2](#2-已知限制)。

**标签**：MCP 特性每次 spawn stdio 服务器时，把"这个 PID = 某个服务器"存进平台层的进程登记簿（[`src/host/platform/process-registry.ts`](../src/host/platform/process-registry.ts) —— 特性之间禁止互相 import，登记簿放在双方都能 import 的平台层）。存的是**配置里的服务器名**而非注册 ID——工作区级服务器的 ID 是 `ws-` 加 sha256 哈希、全局级是随机 base64，都是给机器对账用的，人读不出来，也没法与 `/mcp` 选择器里的名字对上；工作区级服务器再带上工作区目录名（`名字@工作区`），因为同一个服务器名可以在两个工作区里各跑一份。展示时标签沿树**继承**：Windows 下登记的是 cmd 包装进程的 PID，它下面真实的 node 服务器靠继承拿到同一个 `mcp:<名字>`。

### 2. 应用组：进程树之外的那半个应用

宿主子树只回答「dsh 拉起了什么」，回答不了「宿主所在的桌面应用一共占多少」。在本次 Electron 桌面样本中，真正拥有窗口的主进程是宿主的同名祖先，renderer、GPU、utility 等同名进程位于宿主之外，从 `process.pid` 向下遍历无法到达。报告器因此在子树之外再算一个**应用组**（`app` 字段，使用同一帧对差分），用于与任务管理器「应用」行对账。

应用组是**同名可执行文件启发式规则**，不是 Electron 角色识别器：

- **候选根**：从宿主沿 `ppid` 向上走，只有父进程的可执行文件基名与宿主相同（大小写不敏感）才继续，最多 8 跳；把到达的**最后一个同名祖先**作为候选根。遇到异名、父进程缺失或 PID 环就停止，异名祖先本身不会成为应用根。
- **向下收集**：从候选根遍历所有后代，即使中间经过异名进程也继续向下；只有可执行文件基名与根相同的进程才计入应用组。向上只认同名链，可避免把终端启动的宿主一路爬到 `explorer.exe`。
- **平行分支条件**：应用组中至少要有一个不在宿主子树内、也不在向上爬过的宿主祖先链上的同名进程。若整条链只有同名启动器祖先 —— 例如 `npm run` 的 node 拉起 dsh 的 node —— 则 `app = null`。没有同名祖先时同样为 `null`；POSIX 与 `dsh web` 都不是被代码强制为 `null`，仍取决于实际进程链。
- **两个集合**：`app.entries` 是应用组中不在宿主子树内的行，页面把它们并入同一棵树；`app.totals` 是整个同名应用组的合计，包含宿主及宿主子树内的同名进程，不包含 `cmd.exe` 等异名子进程。因此它不等于简单的「dsh 总 + 灰点行」。
- **对账边界**：该规则以本次 Windows 实测中任务管理器的应用分组为依据，但代码无法保证所有 Windows 版本、外壳和启动方式都与任务管理器永远同集合。对账时应同时核对进程 PID，不把「同一进程集合」当成无条件保证。

一次实测（2026-11，本机 Windows，dsh 桌面端）：`DeepSeek Harness (5)` = 主进程 + 宿主 + renderer + GPU + utility；页面子树 4 行 / 353 MB 工作集，应用组 5 个进程 / 866 MB 工作集、**482 MB 专用**，任务管理器另一次读取为 **501 MB**，差值来自读取时刻不同。更细的逐行对账见 [三、3.1](#31-桌面端实测5-个同名进程)。内存主对账使用专用工作集；工作集含共享页，只作辅助信息，不直接等同于任务管理器的「内存」列。

### 3. 桌面端与 web 端的进程构成

#### 3.1 桌面端实测：5 个同名进程

2026-11-15 本机 Windows 桌面端的一帧样本中，应用组有 5 个同名进程，宿主下面还有 3 个异名子进程：

```text
DeepSeek Harness.exe  主进程（拥有窗口）          ← 本帧树根 = 应用组 rootPid
├─ DeepSeek Harness.exe  renderer（画这一页）
├─ DeepSeek Harness.exe  GPU 进程
├─ DeepSeek Harness.exe  utility 进程
└─ DeepSeek Harness.exe  dsh 宿主（跑插件、拉 MCP） ← 蓝点 + 整行淡色
   └─ MCP / 插件子树：本帧为 cmd.exe、node.exe、conhost.exe（层级以 ppid 为准）
```

**5 是这次实测值，不是固定不变量**。Electron 版本、窗口数量、功能开关和运行状态都可能改变角色与数量；报告器也不解析 `--type=renderer` 等角色参数，只按同名链和平行分支识别应用组。

三个反复出现的"对不上"，可由这张图解释：

| 现象 | 本次样本的原因 |
| --- | --- |
| 任务管理器显示 `DeepSeek Harness (5)` | 对应图中 5 个同名进程。`cmd.exe` / `node.exe` / `conhost.exe` 不属于本页的同名应用组，本次也未被任务管理器折入这 5 个进程 |
| 页面头部写 8 个进程 | 宿主子树 `entries` 有 4 行（宿主 + 3 个子进程），应用组额外的 `app.entries` 有 4 行；合计 `4 + 4 = 8`。宿主已在 `entries` 中，不能再按「5 + 4」重复计算 |
| 「dsh 总内存」不等于「整个应用」 | 前者统计宿主 + 3 个异名子进程，后者统计 5 个同名应用进程；这是两个不同集合。正常流式路径下，两者都不含注脚单列的采样器 |

该帧中，「dsh 总内存 225 MB」= 宿主 209 + cmd 2 + node 13 + conhost 1；「整个应用 专用 531 MB」对应任务管理器父行 **530.6 MB**，逐行内存也一一对应（109 / 62.8 / 141.4 / 209.3 / 7.8 MB，显示值经过取整）。这些数值只描述该次采样，不是运行时的固定配额。

**为什么任务管理器展开后看起来是平铺的**：本次使用的 Windows 任务管理器按**应用身份**分组，只画「应用 → 组内进程」一级缩进，不表达组内的多层 `ppid` 关系；展开后的第一行是聚合值，不是另一个独立进程。需要查看多叉进程树时可使用 Process Explorer。本页则按 `ppid` 建树，父行位于子行上一层；若父进程不在已下发集合中，该行会作为根展示。

因此，两边的**同名应用进程集合**在本次实测中一致，但页面整棵树还包含 3 个异名宿主子进程，不能笼统地说两边所有行集合相同。另有两处展示差异：任务管理器子行顺序跟随当前排序列，本页固定「同层 CPU 降序 → 工作集降序 → PID」；任务管理器不标出哪一行是父进程，本页用缩进表达父子关系。

#### 3.2 独立终端启动的 web 端（`dsh web`）

在常见的独立终端启动场景中，宿主没有符合条件的同名祖先和平行分支，`app` 为 `null`：页面没有灰点的「应用其他进程」行，也没有底部的「整个应用」对账行，树根就是宿主自己。例如：

```text
node.exe（宿主，蓝点 + 淡色）                   ← 树根示例
├─ cmd.exe → node.exe / conhost.exe             （MCP 服务器，紫点 + mcp: 标签）
└─ git.exe / npm.cmd                            （其他插件 spawn 的子进程，绿点）
```

| | 本次桌面端实测 | 常见独立终端启动的 web 端 |
| --- | --- | --- |
| 树根 | 应用组根（本帧为 Electron 主进程） | 宿主自己（示例为 `node.exe`） |
| 灰点行 | `app.entries.length`，本帧为 4 | `app = null`，为 0 |
| 「整个应用」对账行 | `app` 非 `null` 时出现，本帧有 | 无 |
| 头部 N 个进程 | `entries.length + app.entries.length`，本帧为 `4 + 4 = 8` | `entries.length`，即宿主子树行数 |
| 两张「dsh 总」KPI | 统计可发现的宿主子树，不含灰点行 | 仍只统计可发现的宿主子树，不包含独立浏览器或不可达孤儿进程 |

两个容易忽略的点：

- **判据是实际进程链，不是"web 还是桌面"**：同一个 `dsh web` 若由桌面客户端托管（浏览器开 `localhost:3080`、宿主仍是 Electron 的后代），只要满足同名祖先链和平行分支条件，灰点行照样出现；直接终端启动通常没有应用组，但 `dsh web` 命令本身并不保证 `app = null`。
- **独立浏览器不计入宿主范围**：web 页面所在浏览器的 tab / renderer 属于浏览器应用，不是 dsh 宿主子孙，也不是宿主同名应用组，因此本页不统计。桌面端自己的 Electron renderer 则可能属于同名应用组，两者不能混为一谈。

## 四、 生命周期：采样何时启停

这是本特性存在的理由，稳态规则只有一条：**轮询驱动持续采样；轮询停止后，采样助手只保留退出宽限，不长期运行**。

### 1. 五条规则

（1）路由只在被请求时读取采样器，不另设路由级采样定时器。Windows 流式助手启动时会创建一个 `unref()` 看门狗；正常自退后该看门狗会以空转形式保留，在插件卸载或进入 one-shot 降级模式时清理。因此不能描述为“完全没有定时器”，但空闲看门狗不触发采样，也不会阻止 Node.js 进程退出。

（2）Windows 的常驻 PowerShell **自己退休**：每次读都记录"最后有人要数据的时间"，流的每一帧都检查这个时间戳 —— 超过 6 s 没人要数据，helper 自行退出。"关页面 → 轮询停 → 超过宽限后的帧发现无人监听 → helper 退出"，链路里没有一个需要浏览器配合的环节。

（3）插件卸载 / 重载时 `dispose()` 兜底杀掉 helper，它不会比插件活得久。

（4）客户端一侧是本仓库的既有模式：`useEffect + setInterval(1000) + 卸载 clearInterval`。DSH 切走主面板即整树卸载，时钟随之消失。本页还增加了 **`visibilitychange` 隐藏暂停** —— web profile 里切浏览器标签页不会卸载组件，挂着的时钟会在标签页不可见时停表、回可见时立刻读一次再恢复每秒。

（5）in-flight 守卫防止慢读（Windows 首帧最长可等 4 s）叠成请求堆。

### 2. 实测

**采样器**（2026-11，本机 Windows，独立脚本直起流式 PowerShell）：

- 启动到第一帧 **≈ 0.7 s**（含 PowerShell 启动），此后每约 1.2 s 一帧；
- 单帧 314 个进程、约 112 KB 的单行 JSON，`parseWindowsFrame` 一次通过；
- 命令行含换行与中文时 JSON 转义正确，UTF-8 输出无乱码。

**帧对差分**（2026-11，本机 Windows，真实采样器端到端，1 s 轮询模拟页面）：

- 第 1～2 次读取无窗口（首帧尚无前置帧），自第 3 次起宿主 CPU 持续有值；
- 窗口稳定在 1.15～1.21 s（帧间隔），轮询落在两帧之间时重复显示同一组数字，**零窗口空列 0 次**；
- 模拟关页 8 s 再回来：采样器如约自退休重启，第一对帧窗口 3.4 s（真实的跨退休间隔）依然出值，随后恢复约 1.2 s。

**页面级**（2026-11 实测通过，dsh web + 浏览器端到端）：

- 页面打开期间宿主名下多出一对进程（PowerShell + conhost ≈ 102 MB），页面 `meter` 自报 **0.4% · 103 MB · 2 个进程**，与按父子关系直查宿主的外部观测一致；
- 点侧栏会话切走面板：页面组件**即刻卸载**，包在 `window.fetch` 上的轮询计数**当场冻结**——此后不再有 `/process-monitor/sample` 请求；
- 约 **6～7 s** 后该 PowerShell 自宿主名下消失（6 s 宽限 + 一帧周期）；独立复现（不经浏览器）同样成立：停止读取 9 s 后助手 PID 集合为空；
- 排查提醒：只要**任何一个**客户端还开着该页面在轮询（比如另一个浏览器窗口），助手就存活——这是"页面打开才统计"的正确语义，不是泄漏。先看有没有第二处开着的页面（`netstat` 查 `:3080` 的连接方进程），再下结论；
- 重开页面第一秒显示"采样器启动中"，第二秒起有数据，CPU% 自第三秒起有值（首帧无窗口）。

## 五、 验证

### 1. 冒烟

```powershell
pnpm smoke:process-monitor --url "http://127.0.0.1:3080/?token=<token>"
```

脚本先检查 schema、宿主行及首读 `cpuPct === null`，随后每 600 ms 读取一次，直到拿到 `sampledAt` 更新的新帧（最长约 8 s），再检查宿主 CPU 百分比；stdio 服务器在场时还会检查 `mcp:<名字>` 标签。并非固定隔 1.1 s 只读两次。非全绿退出码为 1。

### 2. 交叉印证：拿什么核对页面的数字

Windows 的 CPU 百分比来自 `Win32_Process` 累计时间差分，内存还使用性能计数器中的专用工作集；POSIX 使用 `ps`。印证分两层：**数字本身**找一条不同的 OS 数据通路（性能计数器 / ETW），**口径换算**见下表 —— 大多数"对不上"其实是进程集合、内存字段或采样窗口不同，不宜先断定为数字错误。

#### 2.1 口径换算表

| 工具 | CPU 口径 | 内存口径 | 与本页的关系 |
| --- | --- | --- | --- |
| 本页（dsh 总 / 宿主） | 整机归一（1 核跑满 = `100% / N`） | 优先专用工作集，缺省时回退 `memBytes`；合计的部分缺失规则见 [六、2](#2-已知限制) | 进程范围是**可发现的宿主子树** |
| 本页（整应用对账行） | 整机归一 | 优先专用工作集合计，同时给出工作集合计 | 统计报告器识别的同名应用组；本次 Windows 实测与任务管理器应用行一致，其他环境需核对 PID |
| 任务管理器（进程页 · 应用行） | 整机归一 | 专用工作集合计 | 应用分组一致时，CPU 与内存可按相同口径比较；差值还可能来自采样时刻、窗口和部分字段缺失 |
| 任务管理器（详细信息） | 整机归一 | 默认"内存"列 = 专用工作集 | 同一 PID 可逐进程比较；切到"工作集（内存）"则对应 `memBytes` |
| Process Explorer（Sysinternals） | 整机归一（默认） | `WS` 列（工作集） | `WS` 可与 `memBytes` 比较；`Private Bytes` 是私有提交量，不是专用工作集，不能直接替代 `memPrivateBytes` |
| 资源监视器（resmon） | 整机归一 | 专用 / 提交 / 工作集分列 | 专用列可与本页有专用读数的行比较 |
| `Get-Counter '\Process(*)\% Processor Time'` | **100% = 1 核** | — | 除以逻辑核数后与本页可比 |
| `npx pidusage <pid>` | **100% = 1 核** | RSS | CPU 除以逻辑核数后可比；内存对应 `memBytes`，不是专用工作集 |

三条注意事项：

- **先对齐口径再对齐数字**：任务管理器「进程」页的应用行与本页两张「dsh 总」卡不是同一进程范围。桌面端两者通常相差 GUI 主进程 / renderer / GPU 等进程，应使用树下的**整应用对账行**，并核对应用组识别结果。
- **采样窗口错开**：不同工具的采样时刻和窗口无法严格对齐，忙碌进程会出现正常抖动；空闲进程（如约 0.0～0.3%）以量级一致为准，不宜追求小数位完全相同。
- **验证自排除**：正常 Windows 流式路径中，任务管理器可以看到命令行含 `Win32_Process` 的 `powershell.exe` 挂在 dsh 下，本页把它及其子树汇总到 `meter`。外部对账时应把这部分开销和采样时刻差一起考虑，不能要求差值**恰好等于** `meter`；降级路径和 POSIX 的限制见 [六、2](#2-已知限制)。

#### 2.2 对照工具

下面这段与插件**没有任何共享代码**：纯 PowerShell，自己差分、按整机归一，并读取 `Win32_Process.WorkingSetSize`，用于对照 CPU 与 `memBytes`。把 `$watch` 改成要对照的 PID（页面上有）即可。它**不能直接改一个字段就变成专用工作集对照器**：`Win32_Process` 没有 `WorkingSetPrivate`，该值必须另查 `Win32_PerfRawData_PerfProc_Process`；需要现成的专用值对照时请使用下面的 `pm-top` 或 `pm-watch`：

```powershell
# check-proc.ps1 —— 与插件同口径的独立对照器：整机归一 CPU% + 工作集 MB
$watch = @(12345, 6789)                 # ← 改成本页要对照的 pid
$cores = [Environment]::ProcessorCount
$prev = @{}; $prevAt = $null
Write-Host ("时间     " + (($watch | ForEach-Object { ("pid $_").PadLeft(20) }) -join ''))
while ($true) {
  $now = Get-Date
  $snap = @{}
  foreach ($p in Get-CimInstance Win32_Process) {
    $snap[[int]$p.ProcessId] = @{
      cpu = ($p.KernelModeTime + $p.UserModeTime) / 1e4
      ws  = [double]$p.WorkingSetSize
    }
  }
  $line = $now.ToString('HH:mm:ss') + ' '
  foreach ($id in $watch) {
    $cur = $snap[$id]
    if ($null -eq $cur) { $line += '        (已退出)      '; continue }
    $old = $prev[$id]
    if ($prev.ContainsKey($id) -and $null -ne $prevAt) {
      $dt = ($now - $prevAt).TotalMilliseconds
      $pct = [math]::Round((($cur.cpu - $old.cpu) / $dt / $cores) * 100, 1)
      $line += ('{0,9}% {1,7:N0}MB ' -f $pct, ($cur.ws / 1MB))
    } else {
      $line += ('        —  {0,7:N0}MB ' -f ($cur.ws / 1MB))
    }
  }
  Write-Host $line
  $prev = $snap; $prevAt = $now
  Start-Sleep -Milliseconds 1000
}
```

它首行同样给 `—`（第一帧没有差分窗口），之后按自己的 1 s 循环刷新。两边采样时刻无法严格同步，数字不会逐刻相等；如果长期差出一个固定倍数，先查核数（`$cores`）是否被另一边当成了别的归一基数。

仓库里还有两个现成的按需版本：

- [`scripts/pm-top.mjs`](../scripts/pm-top.mjs)：跨平台 "top"——自动发现监听在 `--port`（默认 3080）上的 dsh 宿主，或用 `--pid` 直指，整棵子树按帧刷新、按 CPU 排序。支持 `--once` 单帧、`--ticks N` 限帧数、`--json` 每帧一行 NDJSON 和 `--interval` 轮询间隔。
  - **同源但独立采样**：脚本直接 import 构建产物里的采样器与报告器（需先 `pnpm build`），所以计算口径与页面一致；但它自己采样，数值仍受采样时刻影响，并非与页面每一帧必然相等。
  - **帧与标签**：`--once` 的 CPU 列是 `-`（首帧无差分窗口），可用 `--ticks 2` 获取差分。脚本拿不到 `mcp:<名字>` 标签，因为登记簿位于 dsh 宿主进程内。
  - **采样器视角**：外部运行时可以看到页面采样器的 PowerShell / conhost；`--no-samplers` 按命令行签名摘除它们，使行集合在正常流式路径下与页面对齐。pm-top 自己的采样助手挂在 pm-top 的 node 下，不属于宿主子树。`--no-samplers` 也会隐藏页面助手，因此不能用它判断宿主是否仍在采样；应直接按父 PID 查询，例如 `Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" | Where-Object ParentProcessId -eq <宿主PID>`。
  - **列与应用组**：`WS` / `PRIV` 分别是工作集与专用工作集，非 Windows 上 `PRIV` 为 `-`。`--json` 每帧除 `entries` / `totals` / `meter` 外还带 `app`；是否非 `null` 由应用组规则决定，不只取决于桌面端或 web 端名称。
- [`scripts/pm-watch.ps1`](../scripts/pm-watch.ps1)：Windows 专用的固定 PID 对照器（`-Watch "pid1,pid2"`），与插件零共享代码，适合做独立印证；功能上已被 `pm-top.mjs --json` 覆盖，留作第二数据源。

## 六、 边界

### 1. 不做什么

- **不杀进程**：这是仪表盘不是任务管理器，没有结束进程的按钮 —— 误点一个 MCP 子进程的后果（重连风暴、半途的 stdio 写入）比收益大。
- **不做存储 / 网络页签**：进程级存储 IO 与网络连接数没有零依赖的可靠来源（Windows 要 ETW / 性能计数器），做出来只能是装饰。CPU 与内存是本特性当前选择保证口径的两类数据。
- **不持久化**：不落盘、不记忆历史；趋势图只保留当前页面内存中的最近 60 个采样点，关页即弃，不声称提供历史诊断。

### 2. 已知限制

- **父进程已死的孤儿可能不可达**：父进程退出或发生 reparent 后，原来的亲缘关系无法靠当前 `ppid` 完整还原；不再位于宿主子树下的进程不会从宿主根被 BFS 发现。
- **应用组只认同名链和平行分支**：宿主与 GUI 主进程必须具有相同可执行文件基名，向上查找还受 8 跳限制。若桌面外壳是另一个 exe（例如宿主是被外壳拉起的 `node.exe`），向上爬第一跳就断，应用组为空、页面回到只有子树 —— 宁可少一组数，也不把 `explorer.exe` 名下整台桌面算成"应用"。
- **专用内存部分缺失时，合计不等于逐行显示值之和**：单行缺少 `memPrivateBytes` 会回退到 `memBytes`；但只要合计中有一行存在专用值，`totals.memPrivateBytes` 与 `app.totals.memPrivateBytes` 就只累加有专用值的行，页面又优先显示该合计。因此部分缺失时，合计可能小于各行走回退规则后的显示值之和；完全没有专用值时，合计才整体回退到 `memBytes`。
- **采样器自排除有路径边界**：正常 Windows 流式路径能在报告时提供当前 helper PID，并从 `entries` / `totals` 排除其子树；one-shot 降级路径没有保存本次 helper PID，POSIX 又在路由读取 `excludePids()` 前结束了本次 `ps` 的跟踪，因此这两条路径不能保证把本次采样器纳入 `meter` 或从行中排除。
- **Windows 的 stdio wrapper**：`shell: true` 让登记簿记下的是 cmd 包装进程的 PID，真实的 node 服务器在下一层。显示不受影响（来源沿树继承），但 wrapper 与服务器仍在运行时都会各占一行，内存各算各的。
- **dsh-mcp-manager 接管时**：本插件不 spawn MCP 子进程，因此没有带 `mcp:` 标签的行；仍位于宿主进程树内的服务进程会以"其他子进程"出现。页面在没有已标记 MCP 行时显示一条说明。
- **HTTP 型 MCP 不在宿主子树**：即使服务进程运行在本机，只要它不是宿主的后代，本页就看不到；纯远程服务则没有对应的本地进程。
- **PID 复用**：OS 会把退出进程的 PID 发给新进程。负增量按"没有窗口"处理（显示 `—`），后续样本会建立新基线；仅凭 PID 不能证明前后两行一定是同一个进程生命周期。
