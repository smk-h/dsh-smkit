本文说明 dsh-smkit 的「进程资源」页：dsh 宿主进程及其全部子进程的实时资源面板 —— CPU（按整机容量归一）、内存（驻留集）、累计 CPU 时间、命令行。页面打开时采样、关闭后彻底停止 —— 不留定时器、不留后台进程。

## 一、 它是什么

### 1. 解决什么

dsh 内部拉起了哪些进程（MCP stdio 服务器、各插件 spawn 的 shell / git / npm、Windows 下 stdio 命令的 cmd 包装），各自吃多少 CPU、多少内存，此前没有任何一个界面能回答。这个页面把答案放进 dsh 自己的「更多」菜单：点开「进程资源」一行，就是宿主进程整棵子树的实时占用表。

### 2. 入口在哪，为什么没有开关

入口在左栏「更多」菜单（四宫格图标展开）里的「进程资源」行，与宿主自己的「浏览更多插件 / 创建你的插件」同列，点击切换出一块主面板。不占左栏图标条的独立图标——诊断页是偶尔打开的东西，不值一个常驻启动位；曾经评过另外三个落点（账号弹出菜单硬编码不可插、设置弹窗太窄、会话「···」菜单语义是"当前会话的操作"），更多菜单是唯一形态与语义都合适的。

技术形态：行组件优先复用宿主 `MenuItemButton`（`sidebar.panellist.actions` 座位，宿主插件菜单行用的同一个）；宿主模块表没有该导出时回落为本特性自带的一行，样式按宿主菜单行 `.item` 的实测值对齐（13px/34px、radius 12、hover 同 token，实测逐项一致）。切换面板走 `ctx.layout.selectPanel`——经反射在点击时取用，宿主没有 layout 服务时只损失这一次点击，不影响插件激活。

**没有设置开关**，这是有意的：调试页需要一个开关是因为它的存在本身有含义要控制；这个页面的全部开销 —— 包括宿主侧的采样 —— 都被"页面打开"这个动作限定住了，关闭即零开销的东西不需要开关决定它可不可以存在。

### 3. 页面构成

页面按评审定稿的版式实现（仅「子树 CPU 构成」卡一项评审后裁掉，见总览带一条）：

- **头部**：标题 + 「采样中」心跳脉冲徽章（页面隐藏时变「已暂停」、采样器启动期为「启动中」）+ 元信息行（N 个进程 · 1 秒/次 · N 核归一）+ 刷新。
- **总览带**：四张 KPI 卡占满——「dsh 总 CPU / dsh 总内存」（宿主 + 全部子进程的合计，即整个 dsh 服务进程树；悬停有口径说明）与「宿主 CPU / 宿主内存」（仅宿主进程本身），大数值 + 右下角一分钟迷你趋势线（页面内存里留最近 60 个采样点，不落盘、关页即弃）。初版左侧还有一张「子树 CPU 构成」三色堆叠条卡，评审后去掉——三个份额的混合读不出可行动的结论，KPI 卡与分组头聚合已把同样的数说得更清楚。
- **三组可折叠分组卡**（组头：色点 + 名称 + 进程数胶囊 + 聚合「CPU% · 内存」）：
  - **宿主进程**：dsh 主进程本身（树根），整行淡色强调；
  - **MCP 服务器**：本插件拉起的 stdio 服务器子树，每行带 `mcp:<服务器名>` 紫色胶囊（工作区级服务器为 `mcp:<服务器名>@<工作区名>`；沿树继承，Windows 下 node 服务器坐在 cmd 包装下面）；
  - **其他子进程**：树里其余的一切 —— 其他插件 spawn 的命令、openspec 的 git/npm、通知的 PowerShell 等。
- **列**：进程名（悬停见完整命令行）/ PID（等宽）/ CPU%（**热力比例条**：<5% 蓝紫渐变、5~25% 琥珀、≥25% 红——满负载进程不读数也能找到）/ 内存 / 累计 CPU（等宽）/ 命令行（等宽弱化）。窄窗口（≤980px）收起命令行列并縱向堆叠总览带。
- **采样开销注脚**：虚线边框条 + 仪表图标 + 加粗数值（`meter` 字段，见下）。

配色全部走 `--smkit-pm-*` 变量（亮色默认、`body[data-ds-dark-theme]` 切暗色），中性面与文字借用宿主 `--dsw-alias-*` 令牌，自动跟随主题；卡片底取 `--dsw-alias-bg-layer-2`（宿主嵌套面的同一层级）、条槽与组头底取边框令牌的半透明 veil，两个半边与主题中心的主题都不用点名。主题中心的 One Dark Pro 会整体重铺这些 alias 令牌（面板落 `#21252b`、画布 `#282c34`），仅数据五色是本页自己的，另以 `body[data-smkit-theme='one-dark-pro']` 块映射到该配色自己的语法色阶（宿主蓝→链接蓝 `#61afef`、MCP 紫→关键字紫 `#c678dd`、其他绿→字符串绿 `#98c379`、琥珀→黄 `#e5c07b`、红→`#e06c75`）。CPU 列出现 `—` 时的语义见 [二、4](#二统计原理)。

## 二、 统计原理

一句话：**OS 内核给每个进程记着两本账 —— 累计 CPU 时间和当前驻留内存；本页的全部统计学只是"每隔一秒读两次账本、相减"**。没有任何工具能"直接测"CPU 百分比，任务管理器、Process Explorer 与本页用的是同一套办法，区别只在怎么读、在哪减。

```
OS 调度器账本（Win32_Process / ps）
   │  常驻 PowerShell 每约 1.2 s 吐一帧全表（单行 JSON）
   ▼
一帧 + 它的前一帧（帧对，由采样器随读取返回）
   │
   ├─ 帧对帧相减 ──────▶ CPU%
   ├─ 从宿主 pid BFS ──▶ 该展示哪些行（子树）
   └─ 查进程登记簿 ─────▶ mcp:<服务器名> 标签
   ▼
GET /smkit/api/process-monitor/sample ──▶ 页面表格
```

### 1. 数据源：OS 的账本，不是"测"出来的

Windows 上通过 WMI 的 `Win32_Process` 读，每个进程一行：

| 字段 | 含义 | 单位 |
| --- | --- | --- |
| `KernelModeTime` + `UserModeTime` | 进程自启动以来累计消耗的 CPU 时间（内核态 + 用户态） | 100 ns |
| `WorkingSetSize` | 此刻实际占用的物理内存页（驻留集，含共享页） | 字节 |
| `ProcessId` / `ParentProcessId` | 自身 pid 与父 pid —— 树的原料 | — |
| `Name` / `CommandLine` | 进程名与完整命令行 | — |

POSIX 上 `ps -axo pid=,ppid=,rss=,time=,args=` 一行一个进程：`time` 列就是累计 CPU 时间（`[[dd-]hh:]mm:ss[.cc]`），`rss` 就是驻留集（KiB）。

这些值是调度器与内存管理器的记账，天然准确；统计工具的工作只剩"怎么读、怎么算"。特别地，`ps` 自带的 `%cpu` 列（自开机平均）刻意不取 —— 它不对应任何一个时间窗的占用率。

### 2. CPU% 是里程表差分

累计 CPU 时间是**里程表**，不是速度表：单独一次读数只说明"这个进程从启动到现在一共用了 3.2 s CPU"，不说明它现在多忙。要得到当前的占用率，必须两次读数相减：

```
CPU% = (里程₂ − 里程₁) ÷ (时刻₂ − 时刻₁) ÷ 逻辑核数 × 100
```

以本机 16 逻辑核为例：某进程在 1.2 s 墙钟里里程表走了 384 ms —— `384 ÷ 1200 ÷ 16 × 100 = 2.0%`。

**为什么除以核数（整机归一）**：不除的话，一个单核跑满的进程显示 100%，除完显示 100/16 = 6.25%。归一后所有进程的百分比**相加最多 100%**，"子树合计"这个数字才有意义 —— 这也是任务管理器采用的口径。

**内存不需要差分**：驻留集是瞬时值（"此刻物理内存里有多少页"），读出来直接用。注意它与任务管理器默认"内存"列（专用工作集）的差是共享页：本页显示的内存会略大于那一列。

### 3. 差分窗口挂在帧上，不挂在轮询上

本特性修过的真问题。Windows 采样器是一个常驻 PowerShell，每约 1.2 s 输出一帧全表；页面每 1 s 轮询一次。轮询落点必然偶尔两次落在同一帧里 —— 早期版本把差分放在路由里（本次读减上次读），撞帧时窗口变成 0 ms，整列 CPU 一起打成"—"，且随相位漂移成串出现，页面上就是"经常性没有统计数据"。

现在**帧对（本帧 + 前一帧）由采样器随读取一起返回**：窗口恒为真实的帧间隔（约 1.2 s），与轮询落点无关；轮询两次读到同一对帧只是重复显示同一组数字，不会清空。POSIX 侧同理 —— 前后两次 `ps` 互为帧对。

### 4. 什么情况下显示"—"

`—` 的语义是"没有可用的差分窗口"，共四种来源：

- **首帧**：还没有前一帧；
- **窗口 < 250 ms**：两次读的是同一帧或时钟噪声；
- **窗口 > 5 s**：页面关过一阵，这对帧跨得太远，平均值会失真；
- **增量为负**：OS 把退出进程的 pid 发给了新进程（pid 复用）。

四种都显示 `—` 而不是 0.0%，更不是自开机平均 —— 差分之前的数字不对应页面上任何一个时间窗，展示它就是撒谎。下一对有效帧自动恢复。

### 5. 子树与 MCP 标签

**树**：OS 记录每个进程的父 pid。报告器从 `process.pid`（即 dsh 宿主进程本身）出发做宽度优先搜索，收出整棵子树 —— MCP 服务器、cmd 包装、conhost、其他插件 spawn 的命令都在其中。采样器自己的子树**不计入行与合计**（仪表不把"看"这个动作算进被测对象，否则打开页面的瞬间就会抬高想测的数字），但也**不悄悄消失**：它被汇总成 `meter` 字段，页面在表格下方明示为一行开销提示。

**标签**：MCP 特性每次 spawn stdio 服务器时，把"这个 pid = 某个服务器"存进平台层的进程登记簿（[`src/host/platform/process-registry.ts`](../src/host/platform/process-registry.ts) —— 特性之间禁止互相 import，登记簿放在双方都能 import 的平台层）。存的是**配置里的服务器名**而非注册 id——工作区级服务器的 id 是 `ws-` 加 sha256 哈希、全局级是随机 base64，都是给机器对账用的，人读不出来，也没法与 `/mcp` 选择器里的名字对上；工作区级服务器再带上工作区目录名（`名字@工作区`），因为同一个服务器名可以在两个工作区里各跑一份。展示时标签沿树**继承**：Windows 下登记的是 cmd 包装进程的 pid，它下面真实的 node 服务器靠继承拿到同一个 `mcp:<名字>`。

### 6. 采样器与报告器的分工

对外的形状是一条只读路由，没有写操作：

```
GET /smkit/api/process-monitor/sample
→ { sampledAt, intervalMs: 1000, platform, hostPid, cores,
    warmingUp?, error?, entries: [{pid, ppid, name, cmdline, kind, mcpServer?,
                                   cpuPct|null, memBytes, cpuMs}],
    totals: {cpuPct, memBytes, count},
    meter: {cpuPct|null, memBytes, count} | null }
```

- **采样器**（[`src/host/features/process-monitor/sampler.ts`](../src/host/features/process-monitor/sampler.ts)）把 OS 进程表读成归一化的行（pid/ppid/name/cmdline/memBytes/cpuMs）并维护帧对：
  - **Windows**：**常驻流式 PowerShell**（`Get-CimInstance Win32_Process` → `Select-Object` 七个字段 → `ConvertTo-Json -Compress`，循环里 `Start-Sleep 950ms`）。常驻的原因是一次 PowerShell 启动就要零点几秒，每秒重启一个比留一个贵；脚本开头设 `[Console]::OutputEncoding=UTF8`，中文命令行才不会乱码。流连续两次停摆（4 s 无帧）就**降级为每请求一次性查询**（正确但更贵），本会话内不再回头。
  - **POSIX**：每次请求 spawn 一个 `ps`（几十毫秒，不值得常驻）。`args` 含空格，所以前四列按位置取、剩余整体作命令行。
- **报告器**（[`src/host/features/process-monitor/report.ts`](../src/host/features/process-monitor/report.ts)，纯函数）：给定帧对与宿主 pid，完成收子树 → 剔除采样器 → 查登记簿标 MCP → 差分 → 汇总 totals → 排序。输入相同输出必相同，单测据此钉死每条规则。
- **路由**（[`src/host/features/process-monitor/api.ts`](../src/host/features/process-monitor/api.ts)）：不持有跨请求状态 —— 帧对由采样器随读取返回，路由只做"读一次、算一次、答一次"。

## 三、 生命周期：采样何时启停

这是本特性存在的理由，规则只有一条：**轮询即采样，没有轮询就没有采样**。

### 1. 五条规则

（1）宿主侧**没有任何常驻定时器**。路由只在被请求时读采样器。

（2）Windows 的常驻 PowerShell **自己退休**：每次读都记录"最后有人要数据的时间"，流的每一帧都检查这个时间戳 —— 超过 6 s 没人要数据，helper 自行退出。"关页面 → 轮询停 → 下一帧发现无人监听 → helper 退出"，链路里没有一个需要浏览器配合的环节。

（3）插件卸载/重载时 `dispose()` 兜底杀掉 helper，它不会比插件活得久。

（4）客户端一侧是本仓库的既有模式：`useEffect + setInterval(1000) + 卸载 clearInterval`。DSH 切走主面板即整树卸载，时钟随之消失。本页额外补了一档其它页面都没有的：**`visibilitychange` 隐藏暂停** —— web profile 里切浏览器标签页不会卸载组件，挂着的时钟会在标签页不可见时停表、回可见时立刻读一次再恢复每秒。

（5）in-flight 守卫防止慢读（Windows 首帧最长可等 4 s）叠成请求堆。

### 2. 实测

**采样器**（2026-11，本机 Windows，独立脚本直起流式 PowerShell）：

- 启动到第一帧 **≈0.7 s**（含 PowerShell 启动），此后每约 1.2 s 一帧；
- 单帧 314 个进程、约 112 KB 的单行 JSON，`parseWindowsFrame` 一次通过；
- 命令行含换行与中文时 JSON 转义正确，UTF-8 输出无乱码。

**帧对差分**（2026-11，本机 Windows，真实采样器端到端，1 s 轮询模拟页面）：

- 第 1~2 次读取无窗口（首帧尚无前置帧），自第 3 次起宿主 CPU 持续有值；
- 窗口稳定在 1.15~1.21 s（帧间隔），轮询落在两帧之间时重复显示同一组数字，**零窗口空列 0 次**；
- 模拟关页 8 s 再回来：采样器如约自退休重启，第一对帧窗口 3.4 s（真实的跨退休间隔）依然出值，随后恢复 ~1.2 s。

**页面级**（待人工核对，按上文（1）～（4）逐项验收）：

- 页面打开时 Network 面板每秒一个 `/process-monitor/sample`；
- 切到别的面板后该请求归零，任务管理器里采样用的 powershell.exe 在 ~6 s 内自行退出；
- 重开页面第一秒显示"采样器启动中"，第二秒起有数据，CPU% 自第三秒起有值（首帧无窗口）。

## 四、 验证

### 1. 冒烟

```
pnpm smoke:process-monitor --url "http://127.0.0.1:3080/?token=<token>"
```

隔 1.1 s 读两次：schema 完整、宿主行在场且首读 `cpuPct === null`、第二读宿主有真实百分比、`sampledAt` 在走、stdio 服务器在场时 `mcp:<名字>` 标注齐全。非全绿退出码 1。

### 2. 交叉印证：拿什么核对页面的数字

页面的数字来自 `Win32_Process` 两次采样的差分。印证分两层：**数字本身**找一条不同的 OS 数据通路（性能计数器/ETW），**口径换算**见下表 —— 大多数"对不上"其实是口径不同，不是数字错了。

#### 2.1 口径换算表

| 工具 | CPU 口径 | 内存口径 | 与本页的关系 |
| --- | --- | --- | --- |
| 本页 | 整机归一（1 核跑满 = 100/N%） | 工作集 WS（含共享页） | — |
| 任务管理器（详细信息） | 整机归一 | 默认"内存"列 = **专用**工作集 | CPU 直接可比；内存页面值 ≥ 它（差的是共享页），加"工作集"列后直接可比 |
| Process Explorer（Sysinternals） | 整机归一（默认） | `WS` 列 | 两列都直接可比，还能开"命令行"列找行，最省事 |
| 资源监视器（resmon） | 整机归一 | 专用/提交/工作集分列 | 工作集列可比 |
| `Get-Counter '\Process(*)\% Processor Time'` | **100% = 1 核** | — | ÷ 逻辑核数后与本页可比 |
| `npx pidusage <pid>` | **100% = 1 核** | rss | cpu ÷ 逻辑核数后可比 |

两条注意事项：

- **采样窗口错开**：所有工具的 1 秒窗口不可能对齐，忙进程会有 ±10% 左右的正常抖动，空闲进程（0.0~0.3%）以"量级一致"为准，不要追小数点。
- **验证自排除**：任务管理器里能看到一个命令行含 `Win32_Process` 的 powershell.exe 挂在 dsh 下面；本页不把它计入表格，但表格下方有一行"本页采样器另占 …"的明示（`meter` 字段）。与任何外部工具对账时，差值应该**恰好等于**这行提示 —— 差值对不上才是有问题。

#### 2.2 对照工具

下面这段与插件**没有任何共享代码**（纯 PowerShell，自己差分、同样按整机归一、同样取工作集），把 `$watch` 改成要对照的 pid（页面上有），与页面并排看，两列数字应该贴合：

```powershell
# check-proc.ps1 —— 与插件同口径的独立对照器：整机归一 CPU% + 工作集 MB
$watch = @(12345, 6789)                 # ← 改成本页要对照的 pid
$cores = [Environment]::ProcessorCount
$prev = @{}; $prevAt = $null
Write-Host ("时间     " + (($watch | ForEach-Object { ("pid $_").PadLeft(20) }) -join ''))
while ($true) {
  $now = Get-Date
  $snap = @{}
  foreach ($p in Get-CimInstance Win32_Process) {
    $snap[[int]$p.ProcessId] = @{
      cpu = ($p.KernelModeTime + $p.UserModeTime) / 1e4
      ws  = [double]$p.WorkingSetSize
    }
  }
  $line = $now.ToString('HH:mm:ss') + ' '
  foreach ($id in $watch) {
    $cur = $snap[$id]
    if ($null -eq $cur) { $line += '        (已退出)      '; continue }
    $old = $prev[$id]
    if ($prev.ContainsKey($id) -and $null -ne $prevAt) {
      $dt = ($now - $prevAt).TotalMilliseconds
      $pct = [math]::Round((($cur.cpu - $old.cpu) / $dt / $cores) * 100, 1)
      $line += ('{0,9}% {1,7:N0}MB ' -f $pct, ($cur.ws / 1MB))
    } else {
      $line += ('        —  {0,7:N0}MB ' -f ($cur.ws / 1MB))
    }
  }
  Write-Host $line
  $prev = $snap; $prevAt = $now
  Start-Sleep -Milliseconds 1000
}
```

它首行同样给 `—`（第一帧没有差分窗口），从第二行起与本页同秒刷新 —— 如果两边长期差出一个固定倍数，先查核数（`$cores`）是不是被另一边当成了别的归一基数。

仓库里还有两个现成的按需版本：

- [`scripts/pm-top.mjs`](../scripts/pm-top.mjs)：跨平台"top"—— 自动发现监听在 `--port`（默认 3080）上的 dsh 宿主，或 `--pid` 直指，整棵子树按帧刷新、按 CPU 排序（`--once` 单帧、`--ticks N` 限帧数、`--json` 每帧一行 NDJSON、`--interval` 轮询间隔）。它不重写口径，直接 import 构建产物里的采样器与报告器（需先 `pnpm build`），所以 CPU%/内存与页面必然一致；代价是拿不到 `mcp:<名字>` 标签（登记簿在宿主进程里，见脚本头注释）。`--once` 帧的 CPU 列必然是 `-`（首帧无差分窗口），要单帧有数字用 `--ticks 2`。它是外部视角，会如实列出插件自己的采样 powershell 及其 conhost（即页面的 `meter` 那 2 个进程）；加 `--no-samplers` 则按签名摘掉它们，行集合与页面完全对齐。
- [`scripts/pm-watch.ps1`](../scripts/pm-watch.ps1)：Windows 专用的固定 pid 对照器（`-Watch "pid1,pid2"`），与插件零共享代码，适合做独立印证；功能上已被 `pm-top.mjs --json` 覆盖，留作第二数据源。

#### 2.3 对照实测

- **单核满负荷**（16 逻辑核）：对照器稳定显示 **6.3%**（= 100/16），空闲父进程 0% —— 差分与归一口径可信。
- **与运行中的 dsh web 实况对照**（2026-11，本机）：轮询本插件接口的同时用独立对照器盯同 4 个 pid，并对宿主加压 6 s —— 两边同为空闲期 ~0.1%、加压期同升至 **2~3.2%**、恢复期同回 ~0.1%，形状与量级一致（±1pp 以内差异来自两边采样窗口不对齐）；18 轮轮询 0 次全空（帧对差分修复后）。
- **页面 vs pm-top 三方对账**（2026-11，dsh web @3080，页面开启状态）：页面 7 行与 `pm-top --no-samplers` 的 7 行** pid 逐一相同**；页面合计 492 MB + meter 104 MB ≈ `pm-top` 默认合计 588 MB（差值来自两次读取间宿主工作集的正常波动）；meter 的 2 个进程正是 pm-top 默认视角里多出的 powershell + conhost 两行。

## 五、 边界

### 1. 不做什么

- **不杀进程**：这是仪表盘不是任务管理器，没有结束进程的按钮 —— 误点一个 MCP 子进程的后果（重连风暴、半途的 stdio 写入）比收益大。
- **不做存储/网络页签**：进程级存储 IO 与网络连接数没有零依赖的可靠来源（Windows 要 ETW/性能计数器），做出来只能是装饰。CPU 与内存是 `Win32_Process` / `ps` 一次查询就诚实回答的两列。
- **不持久化**：不落盘、不记忆历史。昨天的 CPU 列是关于一个已不存在的时间窗的谎言。

### 2. 已知限制

- **父进程已死的孤儿不可达**：OS 不维护"父已死"的链，reparent 之后 ppid 指向已退出的 pid，从树根 BFS 到不了它们。VS Code 自己的进程浏览器同样如此。
- **Windows 的 stdio wrapper**：`shell: true` 让登记簿记下的是 cmd 包装进程的 pid，真实的 node 服务器在下一层。显示不受影响（来源沿树继承），但"wrapper + 服务器"两行都会在表里，内存各算各的。
- **dsh-mcp-manager 接管时**：本插件不 spawn MCP 子进程，"MCP 服务器"组为空；那些服务器仍会以"其他子进程"出现在表里（它们仍是宿主进程的后代），只是没有 `mcp:` 标签。页面在该组为空时显示一条说明。
- **HTTP 型 MCP 无本地进程**：它们根本不在宿主的进程树里，这个页面按定义看不到。
- **pid 复用**：OS 会把退出进程的 pid 发给新进程。负增量按"没有窗口"处理（显示 `—`），下一秒基线自动重建。
